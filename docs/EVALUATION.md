# Duplicate-search evaluation

## Test set

`fixtures/` holds synthetic, fully licensed photos, regenerated by `python scripts/fixtures/generate.py`.
Fictional brands are rendered onto lit cylinders, then "photographed" with varied pose, perspective,
background, white balance, exposure, and blur.

- **Catalogue:** 22 owned items / 30 photos. That includes two owned colourways and 8 items with a back photo.
- **38 queries**, labelled:

| Kind | n | Correct answer |
|---|---|---|
| reshoot (same koozie, new photo) | 22 | the item |
| back (opposite side of an item whose back is indexed) | 4 | the item |
| colorway (known artwork, different body colour, **not owned**) | 3 | no match |
| redesign (same brand, different artwork, **not owned**) | 3 | no match |
| lookalike (different brand, near-identical layout/colours) | 3 | no match |
| novel | 3 | no match |

Synthetic photos are a proxy. They're cleaner than real foam koozies, which crease, reflect, and
get photographed at odd angles. Once real photos exist, label a few dozen known duplicate pairs and
re-run with `--fixtures` pointing at a directory with the same `manifest.json` format.

## How to run

```sh
npm run eval                          # Gemini (needs GEMINI_API_KEY in env or .dev.vars); ~68 embedding calls, free tier OK
python scripts/eval/run_eval.py --provider pixels   # offline control baseline
```

The script embeds once at 3072 dims and caches the result. It then evaluates truncated and
renormalised vectors at 3072 / 1536 / 768 / 512 / 256 dims, which is how Matryoshka embeddings are
meant to be shortened. It reports:

- recall@1 and recall@5
- the true-match score distribution vs. the best wrong-item score
- the separation margin
- suggested `MATCH_STRONG` (just above every wrong-item score seen) and `MATCH_POSSIBLE` (keeps ~95% of true matches)

Reports are written to `scripts/eval/results/` (gitignored).

## Real photos (Wikimedia Commons)

The synthetic set is too clean, so there's also a small set of real, openly licensed koozie photos:

```sh
python -I scripts/corpus/fetch_commons.py     # downloads to fixtures/web-corpus/ (git-ignored), with attribution
python -I scripts/corpus/make_eval_set.py     # 10 catalogue photos, 20 simulated re-shoots, 4 group shots
python scripts/eval/run_eval.py --fixtures fixtures/web-corpus/eval [--provider pixels]
```

It's small because openly licensed koozie photos barely exist. In November 2026 Commons had 14 usable
ones after removing off-topic hits, listed in `fixtures/web-corpus/rejected.txt`. The Openverse
search API (CC-licensed Flickr photos) was timing out. Retail sites (Amazon, Etsy, eBay) have
thousands of listings, but their photos are copyrighted and scraping breaks their terms, so they
weren't used. The re-shoots are simulated (crop, rotation, lighting, blur), so this set tests
robustness to real-world photo quality, not to genuinely different photos.

**The test set that matters is the collector's own collection.** Photographing the 364 existing
koozies (see README, "Photographing the existing collection") produces the catalogue. Re-photographing
30 to 50 of them on another day, in other light, through the normal scan flow, then gives true
re-shoot pairs. The colour and design variants he already owns, like the 20 Amazon Christmas
designs and the three Wrigleyville koozies in two sizes, are the hard negatives a web corpus would
never have. Export the pairs as a fixtures directory with the same `manifest.json` format and run
`run_eval.py --fixtures` on it to set `MATCH_STRONG` and `MATCH_POSSIBLE`.

## Results so far

| Provider | dims | recall@1 | recall@5 | Notes |
|---|---|---|---|---|
| pixels baseline (24×24 pixels + colour histogram) | 1920 | 50% | 88% | Control. Fails on pose/background changes; negatives score as high as positives (margin −0.58). |
| pixels baseline, Commons set | 1920 | 90% | 100% | Easy: only 10 catalogue items, and re-shoots are edits of the same photo |
| gemini-embedding-2, synthetic set | 768 | 96% | 100% | All re-shoots score ≥ 0.88. Same-artwork colourways reach 0.945, so they appear as "very similar" and the user decides. 3072→256 dims change nothing material |
| gemini-embedding-2, Commons set | 768 | 100% | 100% | True matches ≥ 0.87, group shots ≤ 0.77 (margin +0.11) |

Thresholds set from these runs: `MATCH_STRONG 0.94`, `MATCH_POSSIBLE 0.85`. Re-check them with real re-shoots of the collection.

What would make Gemini acceptable for this app:

- recall@5 ≈ 100% on re-shoots: the right koozie must appear in the 5 candidates shown.
- A clear score gap between re-shoots and look-alikes or novel designs.

Colourways and redesigns are expected to score high, since they share artwork, and the app is
designed to show them and let the user decide. If recall@5 falls short:

1. Check whether failures concentrate on back-side queries. If so, encourage indexing back photos.
2. Try a higher dimension.
3. Consider a second-stage comparison with a vision LLM, or a different embedding model, behind the
   `Embedder` interface.
